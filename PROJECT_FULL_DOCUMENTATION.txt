Project summary

- Name: Skill Barter
- Type: Next.js (App Router) + TypeScript web app
- Purpose: Peer-to-peer skill barter (users offer skills to teach and list skills they want to learn); exchanges formed between users, with chat and lifecycle (pending → active → completed)
- Backend: Node.js + Next.js API routes + Mongoose (MongoDB)
- Auth: NextAuth (OAuth providers: Google, Apple + credentials)
- UI: React components, Tailwind CSS
- Dev tooling: Jest (unit), Playwright (e2e), Dockerfile for container builds

High-level architecture

- Frontend pages are Next App Router server/client components. Session is retrieved server-side in layout and passed to SessionProvider as initialSession to avoid hydration flicker.
- API routes under src/app/api handle CRUD: users, skills, exchanges, search, uploads, db-seed/status.
- Mongoose models live under src/models; connectDB helper in src/lib handles Mongo connection.
- Client components (Navbar, Header, Profile forms, Chat, SkillsBrowser, Search result cards) handle interactions and call API routes.
- State: local React state (useState/useEffect). Some pages use polling for real-time-ish behavior (messages every few seconds). API response format standardized to { data, error }.

Important functions & flows (concise)

1. Auth flow
   - NextAuth configured in src/app/api/auth/[...nextauth]/route.ts (Google/Apple/credentials).
   - layout.tsx calls getServerSession(authOptions) and passes session into Providers.tsx -> SessionProvider initialSession. This reduces client flicker.
   - Error sources to watch: NEXTAUTH_URL must match Google console redirect URIs; port mismatches cause OAuth callback errors.

2. Profile flow
   - GET /api/user/profile returns { data: user }, PUT updates profile.
   - Profile page uses fetch wrapper to extract result.data and set local state for user.
   - Skills add/remove endpoints update both Skill collection and user's skillsToTeach/skillsToLearn arrays.
   - Projects/certificates/education/work endpoints follow same pattern (POST/DELETE) and return standardized responses.

3. Skill/Search flow
   - POST /api/skills creates a Skill and pushes its id into user's array (teach or learn depending on type).
   - Search endpoint (src/app/api/search/users/route.ts) performs regex queries and populates skills and basic profile data.
   - Important: current user is excluded from search results (filter by _id: { $ne: currentUserId }).

4. Exchange lifecycle
   - POST /api/exchanges: Creates exchange with offeredBy (initiator) and requestedBy (target), status: "pending".
   - Recipient can accept via PATCH /api/exchanges/[id]/status -> becomes "active".
   - Either or both users can call status endpoint to mark complete (requires both to agree or system rule you implement).
   - Exchange detail route returns populated users and skill objects.
   - Messages: /api/exchanges/[id]/messages supports GET (list) and POST (create); messages stored as subdocs with createdAt timestamp; API returns { data: messages }.
   - Server-side validation prevents self-exchanges; client also disables Start Exchange when card is your own.

5. Chat functions (Chat.tsx)
   - fetchMessages(): GET messages; extracts result.data and sets state.
   - sendMessage(): POST message; expects { data: newMessage } response and appends to messages array.
   - formatMessageTime(): uses createdAt (or fallback) to render relative time; checks for undefined guard.
   - Sender handling: message.sender might be an id or populated object — UI uses senderId extraction and sender name display.

6. Dashboard
   - Aggregates counts: totalSkills is user.skillsToTeach.length (only teach counted as requested).
   - Tiles are clickable and navigate to the relevant pages; quick actions wired to search/profile/exchanges.
   - Dashboard refreshes when exchanges change (refreshKey state or re-fetch after status change).

Known issues previously found & fixed (important for state/hydration)

- Hydration flicker due to client-only session fetching → fixed by server seeding session in layout and passing initialSession to SessionProvider.
- Inconsistent API response formats: some routes returned raw objects while others returned { data, error } — standardized to createApiResponse. Many frontend pages were updated to expect/extract result.data.
- Skill add endpoint used wrong user array previously → fixed to add to skillsToLearn vs skillsToTeach based on 'type' param.
- Exchange model/schema mismatch: APIs originally used participants array; code was refactored to use offeredBy/requestedBy. All related routes updated (messages, status, listing).
- Chat errors:
  - messages.map is not a function → fixed by extracting result.data array.
  - timestamp vs createdAt mismatch → standardized to createdAt and types updated.
  - Rendering sender object directly → fixed to display sender.name or fallback.
- Search originally used Atlas $search aggregation — replaced with regex queries for local MongoDB compatibility.
- OAuth callback errors: NEXTAUTH_URL must match Google Console redirect URIs; handled in docs and env.

State management diagnosis

- App uses local React state with many controlled forms; there is no global store (Redux/React Query).
- Problems arose when API responses had inconsistent shapes, causing components to set wrong state shapes.
- Some components recreated handlers per render causing extra re-renders; memoization (React.memo/useCallback/useMemo) applied to Navbar/MobileNavbar/handlers to lower churn.
- Recommendations: adopt SWR or React Query for server state (skills, exchanges, profile). That centralizes caching, optimistic updates, background revalidation and simplifies re-rendering logic.

Security & privacy notes

- Passwords must be hashed (NextAuth handles credentials strategy if used; check hashing in user registration code).
- Admin endpoints must be protected (server-side checks using getServerSession and authorize against session.user.isAdmin).
- Never expose raw JWTs or sensitive data in API responses. Always return minimal user info (id, name, avatar, public links) unless authorized.
- Validate inputs (server-side) for all POST/PATCH — file uploads, links, dates.
- Rate limit auth endpoints (you already had rate-limiter concerns referenced).

Where to look first when something breaks

1. Check dev server console for stack trace.
2. Confirm API response shape using browser Network tab; ensure frontend expects result.data.
3. Check getServerSession usage: all server-side endpoints must pass authOptions when calling getServerSession.
4. Verify Mongoose model imports on any route that uses .populate('Skill') — MissingSchemaError points to missing import.
5. Confirm NEXTAUTH_URL vs Google redirect URIs when OAuth issues occur.
